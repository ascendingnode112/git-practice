What GitHub Adds to Git

Lesson 0002 · ~12 minutes · git-practice

Everything in Lesson 1 happened on your machine. Git needs no network, no account, no GitHub — commits, branches, and history are all local. So what is GitHub, exactly? This lesson gives you the map, then you'll push real commits through it.

The idea: a second copy, plus a collaboration layer

A remote is a copy of your repository stored somewhere else — same snapshot chain, same history. GitHub is a hosting service that holds remotes and wraps tools around them: pull requests, issues, forks. (GitHub Docs, "About remote repositories")

Local repositorythis machine — full history
push →
← fetch / pull
Remote "origin"github.com — a full copy

Your repo is already wired up. Run git remote -v and you'll see:

origin  https://github.com/ascendingnode112/git-practice.git (fetch)
origin  https://github.com/ascendingnode112/git-practice.git (push)

origin is not magic — it's just the conventional nickname for the remote you cloned from or added first, so you don't type the URL every time. (Pro Git §2.5) Three commands move snapshots between the two copies:

  • git push — uploads local commits the remote doesn't have. Commits only: uncommitted edits never leave your machine, no matter how often you push.
  • git fetch — downloads new remote commits but changes none of your files. Always safe; it's how you look before you leap.
  • git pull — fetch plus a merge into your current branch. This one does change your files.
Decoding git status: yours says add-notes...origin/add-notes. That means your local branch is linked to its copy on GitHub (a tracking branch), and Git will report "ahead by 1" when you have a commit the remote lacks. That line is your push/pull compass — after this lesson you'll be able to read it.

The collaboration layer

On top of hosting, GitHub adds workflow tools that live on the website, not in Git:

  • A pull request is a request to merge one branch into another, with review and discussion attached. The name reads backwards — you're asking the target branch to pull in your branch. (GitHub Docs, "About pull requests")
  • A fork is your own server-side copy of someone else's repo — push freely to yours, then PR back to theirs.
  • An issue is a tracked discussion (bug, task, question) attached to the repo.

Now do it for real

This drill includes Lesson 1's skill — stage, commit — because your teaching workspace files are still untracked. You'll snapshot them locally, then move that snapshot to GitHub. Predict every git status before reading it. 

# 1. Confirm the wiring you read about.
git remote -v
git status          # predict: untracked files; branch in sync with origin/add-notes

# 2. Lesson 1 skill: assemble and take the snapshot (local only!).
git add .
git commit -m "Add teaching workspace"

# 3. Read the compass line.
git status          # predict: "ahead of 'origin/add-notes' by 1 commit"

# 4. Is the commit on GitHub yet? Check without changing anything.
git fetch
git status          # predict: still ahead by 1 — fetch found nothing new, push sends, fetch receives

# 5. Send the snapshot up, then re-read the compass.
git push
git status          # predict: "up to date with 'origin/add-notes'"

# 6. See the same commit on the other copy.
gh repo view --web  # switch to branch add-notes on the site; find your commit

Stretch goal, if you want to touch the collaboration layer today: run gh pr create --web and you'll see GitHub propose merging add-notes into main — that's a pull request taking shape. You can close the tab without creating it; we'll do the full PR-and-merge loop in a later lesson.
