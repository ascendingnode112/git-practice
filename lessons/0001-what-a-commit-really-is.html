What a Commit Really Is

Lesson 0001 · ~10 minutes · git-practice

You've already made two commits in this repo by following steps. This lesson replaces the steps with the model underneath, so that git status output stops being noise and starts being a map. One idea, then you practice it for real.

The idea: snapshots moving through three areas

Git stores your project as a chain of snapshots. A commit is not a diff, not a patch, not "the changes" — it is a full picture of every tracked file at one moment, plus a pointer to the snapshot before it. Git shows you diffs because they're easier to read, but that's presentation, not storage. (Pro Git §1.3)

Every change you make travels through three places:

Working directorythe files you edit
git add →
Staging areathe next snapshot, assembled
git commit →
Repositorypermanent snapshots (.git)
  • Working directory — your actual files. Editing here changes nothing in Git's history.
  • Staging area — a loading dock where you assemble the next snapshot. git add copies a file's current state here. This is why you can edit five files but commit only two.
  • Repository — the .git directory, where git commit files the assembled snapshot away permanently.
The confidence unlock: once a change is committed, it is nearly impossible to lose. Git keeps snapshots even through most mistakes. Real danger only exists for work that was never committed. This is why the pros commit early and often — every commit is a save point. (Pro Git §1.3)

One subtlety worth knowing now: git add copies the file as it is at that moment. If you edit the file again afterward, the new edit is back in the working directory only — the staged copy is the older version until you add again. git status will show the same file in both lists, which looks like a bug until you know this.

Now do it for real

In a terminal, in ~/git-practice. The feedback loop is git status — run it after every step and predict what it will say before you look. 

# 1. Look at where you are. Two snapshots exist already.
git log --oneline
git status          # predict: your new lesson files listed as "Untracked" —
                    # Git sees them but snapshots nothing until you git add them

# 2. Edit README.md — add any line. Where does the change live now?
echo "Learning the three areas" >> README.md
git status          # predict: "Changes not staged for commit"

# 3. Move it to the staging area.
git add README.md
git status          # predict: "Changes to be committed"

# 4. Edit the SAME file again — the subtlety from above.
echo "A second line" >> README.md
git status          # predict: README.md appears in BOTH lists. Why?

# 5. Stage the newer edit too, then snapshot it.
git add README.md
git commit -m "Practice the three areas"
git log --oneline   # predict: three snapshots now

If every git status matched your prediction — that's the whole game. You just read Git's map instead of following steps.
