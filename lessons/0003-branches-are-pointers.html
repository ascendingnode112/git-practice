Branches Are Pointers

Lesson 0003 · ~12 minutes · git-practice

You've been on a branch called add-notes since this repo began, without needing to know what a branch is. Here's the payoff idea — smaller and stranger than most people expect — and it's the last piece you need before merging your work into main with a real pull request.

The idea: labels on snapshots, not containers of files

A branch is a movable pointer to one commit. Not a copy of your code, not a folder, not a parallel universe — a 41-byte file containing a commit hash. That's the entire implementation. (Pro Git §3.1) Your repo, right now, drawn honestly:

mainorigin/main 7934de5
←
 5738bc2
←
 46a43e2
←
HEADadd-notesorigin/add-notes f89d8f9

One history. The pointers just sit at different places in it.

  • A branch (main, add-notes) is a label on a commit. When you commit, the branch you're on slides forward to the new snapshot. Nothing else moves it.
  • HEAD is the "you are here" marker — it points at your current branch. Notice main is still back at the initial commit: nobody has committed while standing on it.
  • git switch does two things: repoints HEAD, and rewrites your working directory to match that branch's snapshot. Files tracked only on the other branch vanish from disk — and come back when you return. Nothing is ever lost; you're choosing which snapshot is unpacked.
The pointer you already met: origin/main and origin/add-notes are remote-tracking pointers — your local, read-only record of where each branch was on GitHub at last contact. They are not live. main is your branch; origin/main is your note about GitHub's copy of it. They drift apart until a fetch, push, or pull updates the record. (Pro Git §3.5)

Now do it for real

Fair warning for step 4: when you stand on main, every lesson file — including the one you're reading — disappears from disk, because main's snapshot predates them. Your browser has this page loaded, so don't reload until you've switched back. Predict every output first. 

# 1. Housekeeping reps (lessons 1–2): snapshot the glossary + learning records, send to GitHub.
git status          # predict: NOTES.md + assets/course.css modified; GLOSSARY.md,
                    # learning-records/, and this lesson's files untracked
git add .
git commit -m "Add glossary, learning records, and lesson 3"
git push
git status          # predict: clean, up to date with origin/add-notes

# 2. Read the map. Find all five pointers from the diagram above.
git log --oneline --all --graph
git branch -a -v    # note: main is still at 7934de5 — three snapshots behind you

# 3. Proof that a branch is just a file with a hash in it.
cat .git/HEAD                    # predict: ref: refs/heads/add-notes
cat .git/refs/heads/add-notes    # predict: the full hash of your newest commit
git log -1 --format=%H           # same hash. That 41-byte file IS the branch.

# 4. The dramatic part: switch to main and watch the directory obey the pointer.
git switch main
ls                  # predict: lessons/, assets/, GLOSSARY.md... all gone. README.md remains.
git log --oneline   # predict: ONE commit — history reachable from main's pointer only

# 5. Switch back. Everything returns — the snapshots never went anywhere.
git switch add-notes
ls                  # all back

# 6. Prove branch creation copies nothing: make one, inspect it, delete it.
git switch -c scratch
cat .git/refs/heads/scratch      # predict: identical hash to add-notes — same commit, new label
git switch add-notes
git branch -d scratch            # deletes the label; no commits harmed

If step 4 felt safe instead of alarming, the model has landed: switching branches is choosing which snapshot is unpacked into your working directory. The commits themselves are permanent.
